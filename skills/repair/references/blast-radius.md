# Blast radius checklist

Before editing, map who and what depends on the thing you're changing. Most
"the fix broke something else" incidents come from a consumer nobody looked at.

## How to find consumers

- **By symbol:** search for the function, class, type, or constant name.
  Include re-exports and aliases (`export { foo as bar }`, `import x as y`).
- **By string:** dynamic lookups don't show up in a symbol search. Search for
  the name as a string too: `getattr`, `obj[key]`, dependency-injection tokens,
  serializers, ORMs, templates, routes, event names, i18n keys.
- **By file path:** build configs, test globs, Dockerfiles, CI workflows,
  scripts and docs that reference the file.
- **Across languages:** a backend field rename can break frontend code, SQL,
  analytics queries, mobile clients, or a cron job in another directory.
- **Outside the repo:** public APIs, published packages, webhooks, stored data
  and message queues have consumers you cannot search. Treat their contracts as
  frozen unless the user agrees otherwise.

Use your editor's or language server's "find references" when available, and
also run a text search: each one catches things the other misses.

## Checklist by change type

### Function or method
- [ ] All call sites found (direct, via callbacks, via dynamic dispatch)
- [ ] Return value: same type? Same shape? Same null/empty behavior?
- [ ] Errors: does it now throw where it didn't (or stop throwing where callers
      relied on it)?
- [ ] Side effects: logging, I/O, mutation of arguments, caching, events
- [ ] Ordering and timing: sync vs async, call count, idempotency
- [ ] Performance: complexity or number of queries/network calls changed?
- [ ] Overrides and implementations in subclasses or interface implementers

### Type, interface, or schema
- [ ] Every construction site and every read site
- [ ] Serialization/deserialization (JSON, protobuf, DB rows, cache entries)
- [ ] Existing persisted data still valid? Is a migration needed?
- [ ] Generated code (clients, ORM models, GraphQL types) regenerated

### Database
- [ ] Migrations are reversible and safe on existing rows
- [ ] Queries, indexes, views, triggers and reports that use the column/table
- [ ] Other services or jobs reading the same tables

### Configuration, environment, feature flags
- [ ] Every environment (dev, test, CI, staging, production) still has a
      valid value
- [ ] Defaults when the key is missing
- [ ] Other services sharing the config

### Dependencies
- [ ] Changelog read for the version range you're crossing
- [ ] Lockfile regenerated by the package manager, not edited by hand
- [ ] Transitive dependency changes reviewed

### Concurrency and shared state
- [ ] Globals, singletons, module-level caches
- [ ] Locks, transactions, retries, and what happens under parallel calls
- [ ] Test isolation: does your change leak state between tests?

### UI and styling
- [ ] Every place the component, class or token is used
- [ ] Responsive sizes, dark mode, accessibility (focus, labels, contrast)

## Hyrum's Law: consumers of the bug

> With enough users, every observable behavior of your system will be depended
> on by somebody.

Before changing buggy behavior, search for code that **works around** it:
extra null checks, compensating offsets (`- 1`), retries, swallowed errors,
comments like "workaround" or "hack" or "TODO", or a reference to the bug.
Fixing the bug can break the workaround, so update or remove workarounds in
the same change.

## Summarize before editing

| Changing | Consumers | Behavior they rely on changes? | How it will be verified |
|----------|-----------|-------------------------------|-------------------------|
| `total()` return when discount null | `checkout.ts:40`, `invoice.ts:12`, `report.sql` | Yes: was a crash, now 0 discount | new unit tests + existing invoice tests |

Any row without a verification method is unmanaged risk. Cover it with a test,
check it by hand, or tell the user.
